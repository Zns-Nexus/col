Protocol and deployment details from the report

The report identifies specification 2026-07-28 and TypeScript SDK v2 as its September baseline. It recommends @modelcontextprotocol/server and the official createMcpHandler entry point.

Modern and legacy clients may negotiate different protocol eras. Test actual host versions. Do not mix v1 imports with v2 registration code or assume a hosting adapter supports every combination.

Streamable HTTP may use request-scoped SSE replies; that differs from the earlier separate HTTP+SSE transport. Ordinary retrieval needs no persistent session store or sticky routing.

Deployment path: catalogue tools, snapshots, MCP Inspector, stable HTTPS endpoint, actual client tests, ChatGPT developer-mode evaluation, then plugin packaging.

These are technical claims recorded in the supplied research, not reverified for this visualization.

The safety boundaries that belong in version one
  • Validate IDs, lengths, filters, result limits, and version combinations. Parameterize database queries.
  • Allow approved ingestion origins; bound redirects, time, and bytes; block private-network destinations.
  • Treat retrieved instructions as untrusted documents. Do not execute examples during lookup.
  • Check tenant and entitlement scope before private retrieval or cache access.
  • Keep secrets out of results and logs; validate credential audiences rather than passing tokens through.
  • Restrict preview origins and avoid arbitrary upstream code in privileged contexts.
  • Keep timeouts, rate limits, output caps, rollback snapshots, and minimal operational logs.

# Col UI documentation MCP and ChatGPT plugin research : September 2026

Research checked on **30 September 2026** for the founders of [Col](https://collection-of-libs.vercel.app/).

**Recommendation:** build a service that helps coding agents discover suitable UI components across libraries and retrieve their verified documentation, dependencies, variants, and setup requirements. Expose that service through one remote MCP server, then package it with a small workflow skill as a ChatGPT and Codex plugin. Add visual selection after the retrieval service works reliably.

The opportunity is narrower than “Context7 for UI.” Context7 already retrieves library documentation, UI vendors already publish MCP servers, and 21st.dev already offers component search with interactive MCP results. Col can compete through the quality of its cross-library catalogue, evidence, and project compatibility information. Whether that advantage attracts repeat users needs a pilot; this research does not establish product market fit.

This report separates **verified facts**, **observations of your live site**, and **proposed choices**. It uses primary documentation, official vendor pages, and your public repository. It is a research and implementation plan, not a completed server, a security audit, or a measured performance comparison. Source pages without a publication date were checked as current documentation; access on this date does not establish when a feature originally launched.

## The product to build

**Proposed promise:** “Find UI components that fit your project, with verified documentation and setup details.” This wording describes the user outcome and allows the same product to serve ChatGPT, Codex, and other MCP clients.

Three jobs should anchor the first release:

1. **Discover:** “Find an accessible React command menu that works with our existing Tailwind setup.” Return a short list with verified constraints and unresolved details.
2. **Inspect:** “What does this animated background depend on, and which TypeScript variant should I use?” Return source-specific setup and API information.
3. **Implement with evidence:** “Use this component in our existing page.” Supply the necessary documentation to the host agent, which inspects and edits the local project using its own tools.

For the last job, the remote Col server should provide facts and documented commands. A coding host can perform local changes. An ordinary chat surface may only be able to explain or generate files. Do not promise identical implementation capabilities on every client.

Start with about **eight well-covered libraries**, selected from your catalogue to exercise different models: copied source, package imports, headless primitives, animated components, and more than one framework if you can maintain them. The number is a proposed scope limit, not a market requirement. Keep broader library discovery available while exposing deeper coverage only where it exists.

For each candidate, distinguish evidence from recommendation. A source may establish keyboard navigation support while leaving screen-reader behaviour in your integration untested. A package manifest may establish dependencies while leaving bundle cost unknown. Label those unknowns instead of converting them into favourable claims.

A useful result should answer:

- What component and library is this?
- Does it match the requested framework and styling approach?
- Is it distributed as copied source, an npm package, or another format?
- Which prerequisites and dependencies are documented?
- Which API/version/variant does the evidence describe?
- Where is the original source, and how fresh is your indexed copy?
- What still needs checking before implementation?

Screenshots, similarity search from images, automatic project migrations, and a universal installer can follow once users need them and the evidence supports them.

## Documentation sources and ingestion

**Proposed ingestion order:** publisher-maintained Markdown or MDX; publisher-provided LLM documentation; structured component registries; and finally permitted HTML extraction. Prefer stable source formats over rendering a website when both provide the same facts.

The llms.txt proposal was revised on 10 August 2026. It describes compact background and links to detailed Markdown, including alternate-link discovery. It remains a proposal: publishing one does not guarantee every host will automatically use it, and it is not authorization to copy content. [llms.txt v2 proposal](https://llmstxt.org/).

shadcn-compatible registries have defined catalogue and item schemas. Their documentation calls for accurate dependencies, registry dependencies, names, and descriptions. Consume those records for compatible components rather than inventing a competing install format. Registries do not represent every UI library or every kind of documentation. [Registry overview](https://ui.shadcn.com/docs/registry), [Registry MCP guidance](https://ui.shadcn.com/docs/registry/mcp), [Registry setup](https://ui.shadcn.com/docs/registry/getting-started).

**Access constraint:** OpenAI requires authorized third-party access and compliance with source terms. It also rejects plugins whose primary function is an unofficial pass-through connector. A public URL alone does not settle permission to ingest or redistribute it. [Plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines).

**Proposed source record:** keep the source location, permitted use and supporting license or permission evidence alongside each ingestion configuration. Verify documentation, code, and media rights separately. Where permission is unresolved, keep a catalogue link and omit copied content until the issue is resolved.

| Record | Minimum useful fields | Reason |
| --- | --- | --- |
| Library | Stable ID, name, aliases, framework, styling, official URLs, distribution model | Resolve names and avoid recommending the wrong ecosystem. |
| Component | Stable ID, library ID, upstream item name, purpose, variants, dependencies, setup, docs URL | Preserve the facts needed to use one item. |
| Documentation section | Library/component ID, title, heading, text, complete example, canonical URL | Retrieve bounded evidence without losing example context. |
| Source snapshot | Revision/tag, upstream version if known, fetched time, indexed time, content hash | Track changes and reproduce what the agent saw. |
| Evidence | Claim, supporting source, verification method/time, status | Separate confirmed facts from editorial assumptions. |

These are logical records, not a prescription to create five database tables. Small datasets can begin as validated generated files.

For copied components, an npm package version may be irrelevant. Use an upstream revision, registry item, or variant identifier instead. Keep “requested version,” “resolved version,” and “source revision” distinct. Never label documentation version-specific merely because a version appeared in the user’s prompt.

Extract sections around component identity and headings. Keep an example with its imports, setup, required styles, and explanation. Do not arbitrarily split a code sample halfway through. Preserve prop names and defaults as the publisher describes them; record the distinction between required and optional props.

Treat extracted documentation as content, including when it contains instructions. An upstream document cannot authorize account actions, change your server configuration, or override the host’s instructions. Do not execute example code during ordinary retrieval.

**Proposed refresh policy:** refresh popular and recently changed sources first, compare content hashes, and replace affected records atomically. Keep a last-known-good snapshot if extraction fails. Tell users when it is stale. A recent fetch timestamp establishes that you fetched a source recently; it does not prove that its documentation matches the newest package release.

Provide a small contribution format so maintainers can supply official source roots, aliases, component inventories, version mappings, and parsing exclusions. Review additions before they enter the trusted catalogue.

## Retrieval and storage

**Proposed starting architecture:** one shared retrieval layer used by the website and MCP, with ingestion outside the tool-call path.

~~~mermaid
flowchart LR
  A[Col catalogue] --> C[Validated catalogue and source snapshots]
  B[Authorized upstream docs and registries] --> I[Refresh and extraction]
  I --> C
  C --> R[Shared retrieval]
  R --> W[Col website]
  R --> M[Remote MCP endpoint]
  M --> H[ChatGPT Codex and other hosts]
  P[Plugin package and workflow skill] --> H
~~~

For catalogue discovery, reuse your existing filters and add a small curated alias list. This can remain file-backed initially. For a growing documentation corpus, one managed Postgres database with full text search is a reasonable first storage/search service; PostgreSQL already provides parsing, indexes, ranking, and highlighting. [PostgreSQL full text search](https://www.postgresql.org/docs/current/textsearch.html).

Use this retrieval sequence:

1. Resolve explicit library names and IDs.
2. Apply hard framework, version, entitlement, and variant constraints before recommending results.
3. Prefer exact component names and API identifiers.
4. Search purpose descriptions and documentation text.
5. Rank using relevance and source evidence, then return a small result set.

For natural-language discovery such as “a subtle animated border around a pricing card,” evaluate how often lexical search misses appropriate candidates. If this is a recurring failure, add embeddings alongside lexical retrieval. pgvector can keep vector search in the same Postgres database and documents ways to combine it with full text search. A separate vector database is not required merely because the server uses AI clients. [pgvector documentation](https://github.com/pgvector/pgvector).

Do not rely on vector similarity for exact API names, version identity, or hard compatibility constraints. If you add hybrid retrieval, retain exact matching and explicit filters. Select any reranker only after it improves your labelled evaluation set enough to justify latency and cost.

Return the minimal relevant sections first, with IDs for follow-up retrieval. A documentation dump can consume the host’s context without helping the implementation. Suggested initial limits are five discovery results and a bounded document response, with server-enforced maximums and explicit truncation indicators.

Avoid crawling sources during every query. An upstream outage should not take your entire discovery service down. Use cached, revision-labelled evidence and an explicit refresh process.

## The MCP tool contract

**Proposed initial surface:** four model-callable tools. These are Col design proposals, not reserved MCP names.

| Tool | Inputs | Result |
| --- | --- | --- |
| search_libraries | Query; optional framework, styling, category | Stable library IDs, fit facts, official links, coverage state. Also resolves aliases. |
| search_components | Purpose or component name; optional library IDs, framework, styling, variant | Ranked component IDs with short evidence-backed descriptions and constraints. |
| get_component | Component ID; optional variant and requested version/revision | Documented setup, dependencies, API/examples where indexed, source links, freshness, and unresolved facts. |
| query_docs | Library ID, question, optional component ID and requested version | Relevant sections and examples with canonical citations and resolved source identity. |

OpenAI recommends tools designed around distinct user goals, with explicit input/output schemas, permissions, errors, stable IDs, and sufficient data for follow-ups. Avoid one generic tool that dynamically exposes arbitrary operations. [Define tools](https://developers.openai.com/plugins/plan/tools).

Keep every tool useful on its own. For example, get_component should return the information needed to inspect an item, not require the user to install a second plugin before it can answer. Deep queries can be served through an internally implemented dependency where authorized.

~~~

Absence of a verified command should produce null or a clear status, not an invented install command. An empty dependency list needs its own verification status if “none” has not been established.

For the initial retrieval tools, explicitly set readOnlyHint to true and destructiveHint to false. Use openWorldHint false only when the operation is confined to a bounded catalogue; use true for an operation that searches or fetches arbitrary public destinations. Annotations are hints, not authorization. [Tool annotation guidance](https://developers.openai.com/plugins/plugin-guidelines).

Declare outputSchema for structured responses and return model-readable text alongside structuredContent. Validate query length, identifiers, enum values, result limits, and version combinations on the server. Distinguish invalid inputs, unknown IDs, unavailable versions, empty results, and temporary upstream failures. [MCP server construction](https://developers.openai.com/plugins/build/mcp-server).

Do not expose a remote install_component tool that suggests it can modify an IDE user’s filesystem. Initially, return documented commands and let the host agent perform project changes within its own permissions.

## The September 2026 MCP baseline

**Verified current baseline:** the official latest specification resolves to **2026-07-28**, released on 28 July 2026. Its major changes include a stateless protocol core, self-contained requests, HTTP routing metadata, cacheable list results, Multi Round-Trip Requests, authorization hardening, and a formal extensions framework. These changes are shipped, not merely the May release candidate. [Current specification](https://modelcontextprotocol.io/specification/2026-07-28), [Release announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

For Col, the practical benefit is simpler remote hosting. Ordinary retrieval should not require a persistent session store or sticky routing. You also do not need long-running task orchestration or server-side model sampling to serve document snippets.

The TypeScript SDK documentation identifies **v2** as its stable line. It uses packages such as **@modelcontextprotocol/server** and **@modelcontextprotocol/client**, whereas v1 examples use **@modelcontextprotocol/sdk** and its subpaths. v2 migration also changes schema handling and several APIs. [SDK v2 overview](https://ts.sdk.modelcontextprotocol.io/v2/), [Migration guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2).

There is an important interoperability detail: using a v2 package does not automatically make a hand-constructed client/server use the new wire protocol. The SDK’s createMcpHandler and serveStdio entry points can support both protocol eras; HTTP legacy handling is stateless by default. Client auto negotiation probes server/discover and can fall back to the earlier initialize handshake. [Protocol versions and dual-era hosting](https://ts.sdk.modelcontextprotocol.io/v2/protocol-versions), [Revision support guide](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28).

The modern protocol’s two standard transports are stdio and Streamable HTTP. HTTP carries requests to one endpoint, with JSON or request-scoped SSE replies. This does not mean “all SSE is obsolete”: the earlier separate HTTP+SSE transport and SSE used for a Streamable HTTP response are different things. [Transport overview](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).

**Recommendation:** start with the current official v2 server APIs and retain legacy compatibility while testing actual hosts. Some OpenAI build examples still use v1 imports. Treat those as valid examples for that SDK line, not imports to mix into a v2 project. The sources inspected do not establish which protocol era every current ChatGPT/Codex/client build selects. Verify the deployed client combinations rather than assuming adoption from a release announcement.

## Building and deploying the server

**Proposed implementation:** retain your Next.js and TypeScript stack, reuse the catalogue, and add an HTTP endpoint over a shared retrieval module. Start with generated catalogue records and a small documentation corpus. Introduce a database when the refresh/search workload needs it.

The official v2 getting-started guide installs the server package with Zod and a TypeScript runner, using Node.js 20 or later. For a separate development prototype, its package baseline is:

~~~sh
npm install @modelcontextprotocol/server zod tsx
~~~

Your existing Next.js project may already supply the build tooling; tsx is useful for an independent script, not a compulsory production dependency. Lock the versions you validate. [SDK server setup](https://ts.sdk.modelcontextprotocol.io/v2/get-started/first-server.html).

Use the official createMcpHandler factory for the HTTP server, register the four tools with full schemas, and connect handlers to your retrieval functions. Keep business logic outside the protocol wrapper so the website can reuse it. Follow the SDK’s current framework/HTTP integration instructions instead of combining a v1 transport example with v2 registration code.

Vercel documents MCP hosting and mcp-handler integration for Next.js and other frameworks. Its MCP overview was updated on 18 September 2026. That supports staying on your current hosting platform; it does not by itself prove that every adapter release supports the latest SDK and protocol combination. If choosing that adapter, verify its package compatibility and test both eras before deployment. [Vercel MCP documentation](https://vercel.com/docs/mcp).

**Recommended deployment sequence:**

1. Implement metadata discovery using the existing catalogue.
2. Add the first verified component/document snapshots.
3. Test the tools directly with MCP Inspector.
4. Deploy a stable HTTPS route, for example your own domain’s /mcp endpoint.
5. Test the deployed endpoint from the actual target clients.
6. Register it in ChatGPT developer mode and evaluate tool selection.
7. Package the plugin only after the server’s behaviour is stable.

An endpoint must actually implement MCP; a conventional JSON search API is not sufficient. Tool discovery, schema validation, results, errors, and the appropriate protocol behaviour must work.

Use scheduled ingestion outside HTTP calls. Store extraction errors and snapshot ages. Keep production credentials in the hosting platform’s secret store. Add request timeouts, sensible rate limits, output-size caps, and a rollback path to the previous valid index. A health endpoint helps operations but does not replace a real MCP tool call as the availability check.

## Creating the ChatGPT and Codex plugin

### Write the workflow skill

**Proposed skill behaviour:**

- Activate for UI library/component discovery or implementation questions.
- If local implementation is requested and file tools are available, inspect the project’s framework, package versions, styling, and conventions first.
- Respect a user-selected library; search alternatives when requested or necessary to explain an incompatibility.

## Adding a visual interface

For a UI discovery product, visual selection could be useful, particularly for animated backgrounds, cards, and marketing sections. Begin with a small comparison gallery after users can successfully retrieve and use components through text tools.

Resources use the text/html;profile=mcp-app MIME type, tools associate UI through _meta.ui.resourceUri, and the interface communicates through the MCP Apps bridge. Existing window.openai aliases remain available; current guidance favours the shared standard for new UI. OpenAI also recommends separating data tools from rendering tools. [Add UI](https://developers.openai.com/plugins/build/chatgpt-ui).

**Proposed UI flow:** search_components returns structured candidates; the model refines the shortlist; an optional render_component_gallery tool shows the final selection. ## Authentication and security

Public, read-only documentation lookup can operate anonymously. Authentication becomes necessary for user-specific data, private sources, saved team preferences, or licensed entitlements. OpenAI’s authenticated MCP path uses OAuth 2.1 with protected-resource and authorization-server metadata, PKCE, resource identity, and supported client registration methods. Its guidance supports CIMD, DCR, and predefined clients. [Authentication guide](https://developers.openai.com/plugins/build/auth).

The 21 August 2026 changelog documents an eligible stable OAuth callback and stable CIMD client ID. They depend on correctly matching issuer metadata and RFC 9207 issuer identification; they are not unconditional strings to paste into every identity provider. Use the current auth guide for setup. [OAuth changelog](https://developers.openai.com/plugins/changelog).

**Recommended first release:** anonymous public retrieval with abuse controls. Add OAuth when an account-backed capability exists, using a maintained identity provider rather than implementing your own authorization server casually. A rate-limit key and an OAuth user identity solve different problems.

Apply these controls to Col’s actual boundaries:

| Boundary | Proposed control |
| --- | --- |
| Tool inputs | Validate IDs, lengths, allowed filters, output limits, and version combinations. Use parameterized database queries. |
| Source ingestion | Allow approved source origins; bound redirects, time, and bytes; block private-network destinations where fetching is involved. |
| Documents | Preserve provenance; isolate untrusted instructions; never execute retrieved examples as part of a lookup. |
| Private content | Authenticate every request and enforce tenant/entitlement scope before retrieval and cache access. |
| Credentials | Use server-held credentials with correct scope; keep secrets out of returned content and logs. |
| Preview UI | Restrict asset/network origins and avoid running arbitrary upstream code in a privileged context. |
| Observability | Log tool names, result IDs, timings, errors, and snapshot revision; minimize and disclose stored query content. |

MCP’s security guidance explicitly rejects token passthrough without proper audience validation and discusses SSRF and state-handle authorization. Carry those boundaries into any future provider integration; a valid upstream token is not automatically a valid token for Col. [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

Recommendations concerning fetch restrictions are an application of those security principles to your ingestion design. This report did not test your deployed security controls.

## Testing the product

Test transport correctness, retrieval quality, and successful implementation separately. A successful tools/list response proves much less than a user obtaining the correct component with workable setup.

MCP Inspector can inspect tool schemas and call tools directly. Use it before host integration to catch protocol and handler errors. [MCP Inspector](https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector).

### Proposed evaluation set

Build a labelled set of **100 queries**, using components that your initial sources actually cover:

| Query group | Cases | What it tests |
| --- | --- | --- |
| Exact component names and APIs | 20 | Identity resolution, aliases, correct source. |
| Natural-language UI intent | 25 | Discovery beyond literal names. |
| Framework, styling, and dependency constraints | 20 | Hard filters and honest unknowns. |
| Version and variant selection | 15 | Avoiding documentation from the wrong release. |
| Follow-up implementation questions | 10 | Enough context to retrieve setup and usage. |
| Unsupported and adversarial requests | 10 | Empty results, injection resistance, restricted access. |

This is a proposed starting benchmark, not a claim that those cases have been run. Store expected source IDs and acceptable alternatives, not one rigid answer sentence. Update the labels when upstream APIs change.

Compare Col against ordinary agent behaviour, Context7, and the relevant vendor/registry MCP where available. Use the same host/model, project, dependency versions, and tasks. Save retrieved evidence separately from generated code so you can distinguish retrieval failures from model implementation mistakes.

For a small implementation subset, use minimal real projects representing your supported stacks. Judge whether the output compiles, imports and renders correctly, uses the documented dependencies, and respects required accessibility interactions. Build success alone does not prove accessible behaviour.

### Measures that matter

Suggested initial targets are planning choices to tune after a baseline:

- A useful, compatible candidate within the first five results for at least 90% of labelled discovery queries.
- Every returned source URL resolves to the claimed source.
- No unflagged mismatch between requested and resolved version in version tests.
- No invented command, prop, or registry item in accepted component records.
- Honest partial/empty/unavailable results for unsupported cases.
- Cached retrieval p95 below two seconds, measured at your endpoint and separately from model response time.

Measure upstream extraction failures, stale-record share, response size, cost per successful task, and how often a developer needs to correct installation details. Do not publish performance figures until measured.

For transport, test the deployed endpoint with a modern SDK client, a legacy client, ChatGPT, Codex, and your chosen additional coding host. Record the actual versions and protocol era. Include auth errors, timeouts, excessive inputs, and refresh failure. If a host lacks UI support, it should still receive useful text/data.

## Costs and business constraints

## Decisions and unresolved questions

| Decision | Recommendation | Change it when |
| --- | --- | --- |
| Generic docs search versus UI focus | Prioritize cross-library component choice and verified setup. | Pilot users consistently need broader documentation coverage that incumbents do not provide. |
| Transport | One remote Streamable HTTP endpoint with tested compatibility. | A specific client or offline use case requires stdio distribution. |
| SDK | Current official TypeScript v2 APIs. | A validated deployment dependency forces a documented temporary v1 implementation. |
| Storage | Reuse catalogue files; add one Postgres service for a growing doc corpus. | Actual refresh/search scale requires more infrastructure. |
| Semantic search | Add after measured intent-query failures. | A labelled evaluation shows material improvement. |
| Authentication | Anonymous for public retrieval; OAuth for private/account features. | The capability needs user identity or entitlement. |
| Installation | Return verified instructions; capable hosts perform local changes. | There is a concrete, safely scoped installation capability to expose. |
| UI | Small optional gallery after text retrieval works. | Users need richer visual inspection and the corpus supports it. |

The unresolved questions that affect implementation are source permissions, the first deep-coverage libraries, supported framework/version combinations, the actual protocol support of target clients, and whether users obtain better results than with existing tools. Those require permission records, client tests, and a pilot rather than further speculative architecture.

**Recommended first concrete milestone:** expose the library and component discovery you already maintain through a read-only MCP, then demonstrate ten successful component-selection and setup tasks across a small verified corpus. Use those results to decide how much documentation ingestion and UI to build next.
